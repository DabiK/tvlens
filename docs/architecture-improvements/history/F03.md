## Défaut

Chaque changement des questions réécrivait leur état complet, et le store gardait une écriture par demande de sauvegarde.

| Situation | Avant (base `0ffdf7b`) | Après (`e6190c2`) | « Avant » établi par |
|---|---|---|---|
| Cent sauvegardes des questions derrière un disque retenu | 100 écritures, 99 états en attente | 2 écritures, 1 état en attente, le plus récent sur disque | Test rouge (sonde) |
| Écriture refusée derrière des demandes regroupées | Une écriture par demande | Une écriture pour le groupe ; chaque demandeur reçoit le refus | Test rouge (nombre d’écritures) |
| Manifeste demandé trois fois derrière une écriture lente | Trois écritures | Une écriture ; le manifeste confirmé est celui du disque | Test rouge (nombre d’écritures) |
| Brouillon d’une réponse | Chaque brouillon réécrit toutes les questions | Publié à chaque fois, sauvegardé au plus une fois par seconde, dernier état compris si la réponse cale | Tests rouges, HTTP et IPC Mac |
| Passage analysé (voie unique), pause, reprise, fichier d’état retenu | Publiés seulement au retour de la sauvegarde ; un client qui interroge reçoit 304 | Publiés tout de suite ; la requête elle-même attend toujours le disque | Tests rouges, cœur et HTTP |
| Sauvegarde refusée pendant la session | Visible au prochain état publié (dette notée en F02) | Publiée dès qu’elle est connue, sa fin aussi | Mutation retenue ; le test est rouge sur la base à une assertion antérieure |
| Session Mac durable en pause | État complet poussé toutes les cinq secondes | Rien n’est poussé | Test rouge |

Deux comportements n’étaient pas des défauts de la base et sont couverts comme garde-fous du changement : un état en attente n’est pas déchiré par un balayage de fenêtre glissante, et le scellement abandonne les états en attente sans rien écrire après lui.

## Déroulé

1. **Exploration en lecture seule.** Chaîne d’appels tracée du client Codex au store, sur les deux hôtes. Les chiffres de l’audit (100 écritures, 6 251 690 octets) n’ont pas été rejoués : leur sonde n’est pas dans le dépôt. Un plan minimal est proposé.
2. **Audit du merger, puis plan amendé par la supervision avant toute écriture.** Quatre décisions changent le plan : copier `history` et `questions` dans l’instantané ; sauvegarder les brouillons au plus une fois par seconde avec rattrapage du dernier état ; garder le balayage Mac pendant la capture ; publier avant de sauvegarder dans le cœur, avec des tests à disque retenu.
3. **Développement**, dans l’ordre store, cœur, hôtes. La suite existante reste à 486 sur 486 après chaque étape, sans test adapté à ce stade. Douze tests sont ajoutés.
4. **Premier échec en suite complète.** Trois suites sont lancées sur le code en préparation : 497 sur 497, 497 sur 497, puis 496 sur 497. Le test Mac existant qui relit un dossier d’archive après une question trouve un fichier `deep-answers.json.tmp` en trop.
5. **Campagnes de répétition, arrêtées.** Le développeur lance des séries de passes pour comparer la base et le code final. La supervision les juge disproportionnées, arrête deux campagnes en cours, interrompt la session et la reprend avec une consigne : diagnostic causal ciblé, une seule suite finale.
6. **Diagnostic causal** par barrière contrôlée, une exécution par arbre (voir plus bas). L’attente du test existant est adaptée et un test de barrière est ajouté.
7. **Suite finale unique**, fichiers exécutés un à un, puis commit `e6190c2`, puis un passage dans la fenêtre Electron native.
8. **Reviews indépendantes** sur `e6190c2` : deux validations à la première passe, six constats non bloquants.

## Le premier échec et sa cause

Une question terminée est écrite deux fois : la réponse, puis la réponse avec ses mesures. Le test existant attendait que la réponse soit sur disque, c’est-à-dire la première des deux écritures, puis lisait le dossier.

Le diagnostic retient la dernière écriture entre son fichier temporaire et son renommage. À cet instant, sur la base comme sur le code final :

- l’hôte a déjà publié la question terminée avec ses mesures ;
- l’ancienne attente du test est déjà satisfaite ; l’attente adaptée ne l’est pas ;
- le dossier contient `deep-answers.json.tmp`, et c’est la seule entrée que l’assertion d’arbre rejetterait ;
- la chaîne d’écritures du store n’est pas réglée ;
- aucune sauvegarde n’est demandée pendant cinq secondes virtuelles.

Une fois l’écriture relâchée : plus de fichier temporaire, arbre identique, aucune écriture dans les cinq secondes suivantes.

Ce que le diagnostic établit, et ce qu’il n’établit pas :

- **Établi.** La fenêtre existe sur les deux arbres : le défaut est dans l’attente du test, pas dans le writer ni dans la minuterie. F03 ne change pas les deux écritures de fin ; il retire l’écriture de progression qui les précédait sur la base (sur la question instrumentée, 7 écritures sur la base, 4 sur le code final).
- **Non établi.** Le même test a aussi échoué sur la base pendant les campagnes, avec une erreur de fichier introuvable pendant la lecture du dossier. Le script du développeur a tronqué le nom du fichier : ces échecs sont compatibles avec la même fenêtre, sans preuve qu’ils en viennent.

Correctif : l’attente du test vise la dernière écriture. Aucune assertion n’est modifiée, les contrôles d’arbre et de fichiers temporaires restent stricts, aucun délai n’est ajouté.

## Ce qui a échoué en route

| Échec | Diagnostic | Correctif |
|---|---|---|
| Quatre nouveaux tests du store rouges sur le code final | Des demandes émises dans le même tour synchrone se regroupent toutes dans la première écriture ; les scénarios supposaient une écriture déjà en vol | Chaque scénario laisse démarrer la première écriture avant d’émettre les suivantes |
| Scénario « fenêtre glissante en pause » jamais satisfait | L’horloge de session s’arrête avec la pause : rien ne devient échu après elle | Le scénario porte sur un passage sorti de la fenêtre juste avant la pause et pas encore balayé |
| Un test HTTP bloque sur la base au lieu d’échouer | Une assertion échoue disque retenu ; la fermeture de l’hôte attend une écriture jamais relâchée | Le double de disque relâche à la fin du test et est créé avant l’hôte |
| Tests de publication verts sur la base à leur première assertion | L’ingestion suivante publiait par son propre balayage | La description d’un passage est retenue et plus rien n’est ingéré ensuite |
| Une mutation laisse un test en attente sans fin | Attente d’une écriture sans borne dans le double de disque | Attente bornée dans le temps, avec un message d’échec |
| Test Mac existant rouge une fois sur trois suites | Voir la section précédente | Attente adaptée et test de barrière |
| Quatre résultats de mutation inexploitables | Le harnais du développeur réutilisait un même dossier temporaire et retenait une sortie ; des exécutions se sont chevauchées | Résultats exclus de la preuve, non relancés |

Incident de procédé : les campagnes de répétition (séries de passes isolées, puis de suites complètes) ont été arrêtées par la supervision. Elles ne comptent pas comme preuve.

## Ce qui a été exercé

- **Node, simulation.** Store réel sur répertoire temporaire, avec des doubles de l’écriture et du renommage pour retenir ou refuser ; cœur avec un port d’archive de substitution ; hôte serveur réel derrière son transport HTTP ; hôte Mac réel chargé avec un substitut d’Electron et des minuteries virtuelles.
- **Mac natif.** Test Electron générique, une fois, sur `e6190c2` : mode simulé, capture synthétique, répertoires isolés, lancé par le développeur à partir d’une copie du script qui n’en diffère que par ses chemins de sortie, redirigés vers un répertoire isolé, et par un chemin d’import. Il couvre le chemin normal (capture, questions, pause, archive, ouverture en lecture seule, reprise, suppression). Il ne couvre ni le disque retenu, ni la cadence des brouillons, ni un refus disque.
- **TV, VPS, fournisseurs.** Non exercés.
- **Latence.** Aucune mesure réelle, ni disque, ni modèle.

## Limites et dettes

| Sujet | Origine | Suite proposée |
|---|---|---|
| La règle de cadence des questions existe en deux exemplaires, un par hôte, avec un délai écrit deux fois | Review standards | La réunir à côté de la composition de conversation que les deux hôtes partagent, ou avec F07 |
| L’indentation d’une écriture est celle de la première demande du tour ; sans effet tant que chaque fichier garde la sienne | Review standards | La porter avec l’état en attente, ou en faire une propriété du fichier |
| La republication après sauvegarde compare le statut de sauvegarde seul ; avec une capture arrêtée faute de place, un état identique peut être poussé une ou deux fois de trop | Review standards, déduit | Comparer la valeur publiée, ou nuancer le commentaire |
| Un état de questions en attente peut être écrit avec une entrée d’activité plus récente que son texte | Review spécification, déduit | L’accepter, ou copier l’activité dans l’instantané de `DeepAsk` (hors fichiers du ticket) |
| Pendant une pause durable côté Mac, les chiffres disque affichés ne sont plus rafraîchis ; les passages à « faible » et « bloqué » restent poussés | Review spécification, déduit | Pousser sur changement des chiffres disque, comme l’hôte serveur |
| Le test Mac de fenêtre glissante repose sur 50 ms d’horloge réelle ; il pourrait échouer sous charge sans défaut du produit | Review spécification, déduit, jamais observé | Élargir la marge sans toucher au produit |
| Échecs Mac vus sur la base pendant les campagnes : fichier non identifié | Développeur | Aucune sans nouvelle observation ; le test de barrière fixe le fait durable |
| Un test du transcripteur local échoue par moments sous charge, sur la base comme sur le commit | Développeur ; hors du diff | Ticket séparé |
| Quatre mutations exclues : la minuterie de rattrapage et le balayage Mac reposent sur les assertions positives des tests | Supervision | Les rejouer avec un dossier par exécution si la preuve est jugée utile |
| L’attache de l’état en attente à sa session, son abandon quand l’hôte lâche la session et sa remise avant fermeture ne sont pas discriminés séparément | Développeur, confirmé par les deux reviews | Aucune : les états finaux étant sauvegardés tout de suite, rien n’attend normalement à la fin |
| L’état de session est écrit en entier deux fois par passage | Direction approuvée | Format incrémental, hors de ce ticket |
| Une question terminée est écrite deux fois | Comportement antérieur | Modifier `DeepAsk` si on veut une seule écriture |
| Après un arrêt brutal en cours de réponse, le brouillon sauvegardé peut avoir une seconde de retard | Décision | Aucune |
| Une pause lancée entre la demande du manifeste final et son écriture se regroupe avec elle et laisse `live` sur disque, comme avant en deux écritures | Dette de F02, déduite, non reproduite | Les hôtes sérialisent leurs transitions et refusent un passage pendant la fermeture ; la review standards note que la pause sur disque plein pendant un passage ne passe pas par cette sérialisation |
| Un état impossible à sérialiser devient un refus suivi par la barrière, sous le libellé « refusée par le disque » | Review standards, déduit | Libellé à préciser si le cas se présente |
| Refus de création de répertoire ou de renommage non exercés ; pas de fsync | Dette de F02 | Inchangée |

## Organisation de la boucle

D’après le contrat documentaire de la boucle et le rapport d’indépendance du merger, lus sans rien exécuter : une fois F03 validé et intégré, la supervision rapporte une autorisation directe de l’utilisateur pour deux sessions actives au plus, sur des sujets sans recouvrement de code produit. Les vagues prévues sont F04 avec F08, puis F09 avec F10 ; F05, F06 et F07 restent séquentiels. Chaque sujet garde son arbre de travail, les intégrations locales restent cumulatives et faites une à une, et à partir de F04 le numéro d’ADR est celui du sujet. Rien de cela ne modifie le code de F03.
