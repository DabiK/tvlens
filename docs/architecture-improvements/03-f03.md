# F03 — Sérialisation complète et file de sauvegardes non bornée

## Contexte

Audit Opus/Astra du code local TV Lens au13octobre2026, incluant les évolutions non publiées. P2 ; Amplification d’I/O et de CPU. Origine : Astra A4 + Opus A1.

Chaque aperçu de réponse sauvegarde tous les jobs ; audio et vision resauvegardent la session entière. Un disque lent accumule les anciennes versions et retarde les états utiles et la fermeture.

## Preuves et limites

Double mémoire : 100 progressions avec 30 réponses de 2000 caractères ⇒ 100 écritures, 6251690 octets sérialisés. Pas de mesure disque ni de délai utilisateur. Opus identifie aussi les poussées IPC Mac et le prune inconditionnel.

Sources à explorer avant modification : `adapters/local-store.cjs:142`, `runtime/headless-runtime.cjs:275`, `app/main.cjs:147`, `core/deep-ask.cjs:149`.

## Direction approuvée

Séparer publication UI et politique de durabilité ; regrouper les états intermédiaires avant sérialisation avec une écriture en cours et le dernier état requis, puis barrières explicites aux transitions terminales, archives et suppression. Conditionner les émissions Mac sans changement.

## Critères d’acceptation

- [ ] Le backlog de snapshots par fichier est borné et les progressions intermédiaires sont regroupées avant sérialisation.
- [ ] Les transitions terminales disposent d’un flush explicite dont l’erreur reste observable ; ordre et atomicité préservés.
- [ ] Publication UI réactive indépendante de la cadence disque ; seal/delete ne ressuscitent aucun fichier.
- [ ] Comparer appels/octets/backlog sur la même sonde avant/après sans promettre une latence modèle.

- app/main.cjs (sauvegardes/émissions)
- core/session.cjs (émissions)

Les changements hors de ces zones doivent être motivés avant modification ; préserver tous les autres travaux.

## Boucle de livraison

1. Session Opus5.5 ultracode fraîche : exploration forcée avec outils de lecture seulement, chaîne d’appels et tests proposés.
2. Implémentation minimale et régression rouge/verte, puis tests hors ligne proportionnés.
3. Reviews indépendantes conformité et architecture, corrections jusqu’à validation.
4. Intégration locale et vérification par la supervision ; sujet suivant ensuite.

## Contraintes

Travaux locaux uniquement pendant l’absence de l’utilisateur : aucun déploiement, push, accès TV/VPS, fournisseur de l’application ou modification d’authentification/données utilisateur. Pas de framework, DB ou modèle nouveau. Conservation jusqu’à suppression, garde de contexte, citations, files bornées, atomicité, idempotence et confinement failclosed restent intacts. Mesures synthétiques identifiées ; aucun gain de latence inventé.
